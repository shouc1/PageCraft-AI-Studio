# AI 商品图智能生成平台 · 需求分析文档

> 版本：v1.0
> 编写日期：2026-07-12
> 项目代号：photo-ai

---

## 1. 项目概述

### 1.1 项目背景

电商运营、市场设计、内容创作者在制作商品主图、营销海报、详情页素材时存在以下痛点：

- **成本高**：单张商品海报人工拍摄 + 后期成本 200~800 元，周期 1~3 天。
- **重复劳动多**：同一商品需要适配不同风格、节日、平台尺寸，设计师反复改图。
- **风格一致性差**：人工产出受设计师状态影响，难以批量保持品牌调性。
- **AI 工具使用门槛高**：Stable Diffusion / 即梦 AI 等工具学习曲线陡，运营人员无法直接使用。

本项目的目标是构建一个面向非技术用户的 **AI 商品图智能生成平台**，用户只需「上传商品图 + 输入一句话需求」，系统即可通过 Agent 自动规划生成方案、推荐风格与 prompt、调用即梦 AI 生成图像，并通过 WebSocket 实时反馈进度。

### 1.2 项目目标

| 目标层级 | 目标内容 | 验收指标 |
|---------|---------|---------|
| 产品目标 | 跑通"上传→需求→生成→结果"最小闭环 | 单张图端到端生成 ≤ 60s |
| 技术目标 | 接入即梦 AI API 真实生图，支持 3 种 workflow | image2image / text2image / inpaint 各 1 个可用 workflow |
| AI 目标 | 引入 LangGraph + RAG，实现 Agent 自动规划 | Agent 能根据需求自动选择 workflow 并生成 prompt |
| 工程目标 | Docker Compose 一键启动 | `docker compose up` 后 3 个服务全部健康 |
| 简历目标 | 可作为简历亮点项目展示 | README + 演示视频 + 在线 Demo |

### 1.3 项目定位

- **不是**：通用 AIGC 平台、Midjourney 替代品、即梦 AI UI 封装。
- **是**：面向电商场景的 AI 商品图 Agent，强调"需求理解→自动规划→生图→反馈"的完整 Agent 闭环。

## 2. 用户角色与使用场景

### 2.1 目标用户

| 角色 | 描述 | 核心诉求 |
|------|------|---------|
| 电商运营 | 不懂设计，需要快速产出主图 | 一句话生成可用图，无需懂 prompt |
| 市场设计 | 懂设计，需要批量出风格变体 | 可控风格、可局部重绘、可复用历史参数 |
| 内容创作者 | 需要海报、配图 | 快速出图、支持文字生成 |
| 求职者（本人） | 简历项目展示 | 体现 AI Agent + 全栈 + 工程化能力 |

### 2.2 典型使用场景

**场景 A：电商主图美化**
> 运营小李上传一张白底商品图，输入"做成夏日清爽风格，适合饮料类目"，Agent 自动选择 image2image workflow，RAG 推荐"清爽夏日"风格模板，生成 1 张主图，耗时 40s。

**场景 B：节日海报生成**
> 设计师输入"双 11 促销海报，红色喜庆风格，带商品图"，Agent 走 text2image workflow，生成带商品的促销海报。

**场景 C：局部重绘修复**
> 创作者上传已有海报，框选商品logo 区域，输入"把 logo 换成品牌字"，Agent 走 inpaint workflow，仅重绘选区。

**场景 D：历史复用**
> 运营想复用上周生成的"极简护肤品"风格，从历史任务中复制参数，一键再生成。

## 3. 功能需求

按四个阶段拆分，每个阶段都是可独立交付的闭环。

### 3.1 第一阶段 · MVP 最小闭环（可展示）

**目标**：不接即梦 API，先用模拟数据跑通产品流程，验证前后端架构。

#### F1.1 图片上传
- 支持上传 JPG / PNG / WebP，单张 ≤ 10MB。
- 前端预览缩略图，显示文件名、尺寸。
- 上传后存到后端 `uploads/` 目录，返回 `image_id`。

#### F1.2 生成需求输入
- 文本输入框：输入一句话需求（如"夏日清爽风格主图"）。
- 风格选择：下拉选择（清爽夏日 / 极简 / 节日喜庆 / 暗黑科技）。
- 生成模式：商品图美化 / 海报生成 / 局部重绘（仅 UI，后端暂不实现）。
- 基础参数：尺寸（1024×1024 / 768×1024）、强度滑块（0.1~1.0）。

#### F1.3 任务创建
- 点击「生成」按钮 → 调用 `POST /api/tasks` 创建任务。
- 任务初始状态 `pending`，后端立即返回 `task_id`。
- 前端跳转任务进度页或在工作台展示进度。

#### F1.4 任务进度展示
- 前端通过 WebSocket 订阅 `/ws/tasks/{id}`。
- 进度阶段：`pending → planning → retrieving → generating → saving → done`。
- 每个阶段显示阶段名 + 百分比 + 时间戳。
- 后端用定时器模拟各阶段耗时（共约 5s）。

#### F1.5 模拟结果返回
- `done` 状态后端返回一张 SVG 模拟图（带风格文字水印）。
- 结果页左侧展示原图，右侧展示生成图。
- 支持"下载结果"按钮（下载 SVG/PNG）。

#### F1.6 结果展示页
- 路由 `/tasks/[id]`，展示单任务详情。
- 包含：原图、生成图、生成参数、任务时间线、状态。
- 顶部「返回工作台」按钮。

### 3.2 第二阶段 · 接入即梦 AI API 真实生图

**目标**：让系统真的能出图，通过火山引擎调用即梦 AI 生图 + 豆包 LLM 做 prompt 扩展，支持 3 种 workflow，并在生图前提供 prompt 确认环节。

#### F2.1 即梦 API 接入
- 后端通过 HTTP 调用火山引擎视觉智能 API（`https://visual.volcengineapi.com`）。
- 鉴权：Access Key + Secret Key（火山引擎 IAM），通过环境变量配置。
- 调用模式为异步任务：
  1. `CVSync2AsyncSubmitTask` 提交任务，获取 `task_id`
  2. `CVSync2AsyncGetResult` 轮询任务状态，获取结果图 URL
  3. 下载结果图到 `results/` 目录
- 支持 4K 分辨率输出，单张图端到端约 10~30s。

#### F2.2 Workflow 管理
- 各 workflow 封装为独立函数，存放在 `backend/app/services/jimeng/` 目录。
- 支持的 workflow（按优先级）：
  1. `image2image` — 商品图风格化（必做，用 `jimeng_i2i_v30` 图生图接口）
  2. `text2image` — 文字生成图（用 `jimeng_t2i_v40` 文生图接口）
  3. `inpaint` — 局部重绘（用即梦 inpainting 接口）
- 每个 workflow 对应一个即梦 API 的 `req_key`，参数由后端填充。

#### F2.3 真实进度推送
- 任务阶段与即梦 API 状态对齐：
  - `pending` → 已创建任务，未提交即梦
  - `planning` → 已选择 workflow，正在填充参数
  - `generating` → 已提交即梦，轮询任务结果
  - `saving` → 即梦完成，正在下载保存结果图
  - `done` / `failed`
- WebSocket 实时推送状态变更。
- 轮询间隔 2s，单次任务最长等待 120s。

#### F2.4 局部重绘（inpaint）
- 前端支持在原图上画蒙版（用 canvas 或简单矩形选区）。
- 蒙版作为额外参数传给后端，连同原图和 prompt 一起调用即梦 inpainting 接口。
- 支持涂抹消除（prompt 为"删除"）和涂抹编辑（prompt 描述生成内容）。
- 仅重绘蒙版区域，保留其他区域。

#### F2.5 错误处理
- 即梦 API 不可达 / 鉴权失败：任务标 `failed`，前端显示"生成服务不可用"。
- 生成超时（>120s）：标 `failed`，显示"生成超时"。
- 即梦返回错误码：记录错误信息到任务，前端可查看。
- 图片下载失败：重试 3 次，仍失败则标 `failed`。

#### F2.6 豆包 LLM 三专家流水线生成 prompt
- 用户输入的一句话太简单（如"夏日清爽饮料主图"），直接给即梦效果差，需要先用豆包 LLM 扩展成详细英文 prompt。
- **采用三专家流水线 + 评审循环**（非单次调用），保证 prompt 质量和全面性。
- 调用方式：火山引擎 ARK 平台，OpenAI 兼容接口，`base_url=https://ark.cn-beijing.volces.com/api/v3`。
- 鉴权：使用火山方舟 ARK 的 `ARK_API_KEY`，通过环境变量配置，不在前端暴露。
- 模型：通过环境变量 `DOUBAO_MODEL` 配置，例如 `doubao-pro-32k` 或已开通的方舟 endpoint id。

**三专家设计**：

| 专家 | 职责 | 输入 | 输出 | System Prompt 要点 |
|------|------|------|------|-------------------|
| 专家 1：商品分析师 | 提取商品卖点、受众、场景 | 用户需求 + 商品图信息 | 结构化 JSON（product_type、key_selling_points、target_audience、usage_scenario、visual_keywords） | "你是电商商品分析专家，提取核心卖点和视觉关键词，输出 JSON" |
| 专家 2：视觉设计师 | 生成详细英文 prompt | 专家 1 分析 + RAG 风格模板（第三阶段加） | positive_prompt + negative_prompt（JSON） | "你是商业摄影 prompt 工程师，生成含主体/风格/光线/配色/构图/背景的英文 prompt" |
| 专家 3：质量评审员 | 检查 prompt 质量 | 专家 2 prompt + 专家 1 分析 | {passed, score, issues, suggestions} | "你是 AI 图片生成质量评审专家，检查卖点覆盖、风格匹配、负面词完整性" |

**流程**：
```
用户输入 → 专家1分析 → RAG 检索 → 专家2生成 → 专家3评审 → 合格？
                                                       ├─ 是 → 进入 awaiting_confirmation
                                                       └─ 否 → 回专家2修改（最多重试 2 次）

awaiting_confirmation → 用户确认 / 修改 prompt → 即梦生成
```

**迭代控制**：评审不通过时，把评审建议拼进专家 2 的输入重新生成，最多重试 2 次，避免死循环。

**进度推送**：任务阶段 `planning` 细分为三步，前端进度面板显示：
```
[1] 商品分析中... ✓
[2] 视觉设计中... ✓
[3] 质量评审中... ✓
[4] 即梦生成中... (60%)
```

**性能预估**：
- 专家 1：~1s，专家 2：~2s，专家 3：~1s，重试 1 次（如有）：+3s
- 合计 4~7s，费用 ~¥0.005/次（豆包极便宜）
- 加上即梦生图 10~30s，整个任务 15~37s

**与第三阶段的衔接**：第二阶段用 if-else 简单编排三步；第三阶段迁移到 LangGraph，三专家直接映射成 `understand → generate → evaluate` 节点，代码结构不用重写。

### 3.3 第三阶段 · LangGraph + RAG Agent

**目标**：从"调接口"升级为"AI Agent"，让系统理解需求并自动规划。

#### F3.1 LangGraph Agent 编排
Agent 作为 LangGraph 状态机运行，节点如下：

| 节点 | 输入 | 输出 | 说明 |
|------|------|------|------|
| `understand` | 用户需求文本 | 结构化需求（商品类型、卖点、受众、场景、视觉关键词） | 专家 1：商品分析师，对应 F2.6 专家 1 |
| `retrieve` | 结构化需求 | 风格知识 + prompt 示例 | RAG 检索 Chroma |
| `select_workflow` | 需求 + 知识 | workflow 名 + 参数 | 决策节点 |
| `generate_params` | workflow + 知识 + 专家 1 分析 | positive_prompt + negative_prompt | 专家 2：视觉设计师，对应 F2.6 专家 2 |
| `evaluate` | prompt + 专家 1 分析 | {passed, score, issues} | 专家 3：质量评审员，对应 F2.6 专家 3，不通过回 `generate_params`（最多 2 次） |
| `submit` | 最终 prompt + API 参数 | task_id | 调即梦 API |

#### F3.2 RAG 知识库
- 向量库：Chroma（本地嵌入式，零运维）。
- 知识内容（手动整理为 markdown / txt）：
  - `kb/电商主图规范.md` — 平台尺寸、白底要求、文字占比
  - `kb/商品海报风格模板.md` — 各风格配色、构图、元素
  - `kb/prompt示例.md` — 正向 prompt 模板库
  - `kb/负面prompt示例.md` — 通用负面 prompt
- `kb/即梦workflow说明.md` — 各 workflow 适用场景、req_key、输入图片/蒙版要求
- Embedding 模型：先用 `sentence-transformers/all-MiniLM-L6-v2`（本地），后续可换 OpenAI。
- 检索 top-k=3，按相似度排序。

#### F3.3 Agent 决策逻辑
- 输入只有文字需求 → `text2image`
- 输入有图 + 文字 → `image2image`
- 输入有图 + 蒙版 → `inpaint`
- 风格 prompt 由 RAG 检索结果 + 用户需求拼接而成。

#### F3.4 知识库管理（可选）
- 提供 `POST /api/kb/reload` 重新索引知识库。
- 提供 `GET /api/kb/search?q=xxx` 调试检索结果。

### 3.4 第四阶段 · 简历项目包装

**目标**：可演示、可复用、可写入简历。

#### F4.1 Docker Compose 整合
- 服务编排：
  - `frontend` — Next.js
  - `backend` — FastAPI

#### F4.2 历史任务管理

- 任务卡片展示：缩略图、风格、模式、时间、状态。

#### F4.3 演示物料

## 5. 数据模型设计

### 5.1 任务表 `tasks`

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT (UUID) | 主键 |
| user_id | TEXT | 预留，MVP 阶段固定 `default` |
| status | TEXT | pending / planning / retrieving / generating / saving / done / failed |
| progress | INT | 0~100 |
| workflow | TEXT | image2image / text2image / inpaint |
| prompt | TEXT | 用户输入 + Agent 生成后的完整 prompt |
| negative_prompt | TEXT | 负面 prompt |
| style | TEXT | 风格名 |
| mode | TEXT | 生成模式 |
| size | TEXT | 输出尺寸 |
| strength | REAL | 重绘强度 0~1 |
| input_image | TEXT | 原图路径 |
| mask_image | TEXT | 蒙版图路径（inpaint 用） |
| result_image | TEXT | 生成图路径 |
| agent_plan | TEXT | Agent 规划过程 JSON |
| error | TEXT | 错误信息 |
| created_at | DATETIME | 创建时间 |
| updated_at | DATETIME | 更新时间 |
| completed_at | DATETIME | 完成时间 |

### 5.2 任务事件表 `task_events`

用于记录任务时间线，驱动 WebSocket 推送。

| 字段 | 类型 | 说明 |
|------|------|------|
| id | TEXT (UUID) | 主键 |
| task_id | TEXT | 外键 |
| stage | TEXT | 阶段名 |
| message | TEXT | 阶段描述 |
| progress | INT | 当前进度 |
| timestamp | DATETIME | 事件时间 |

## 8. 约束与假设

### 8.1 约束
- 需开通火山引擎账号并开通"即梦 AI"服务，获取 Access Key + Secret Key。
- 需在火山引擎 ARK 平台开通豆包大模型服务，并配置 `ARK_API_KEY` 和 `DOUBAO_MODEL`。
- 调用即梦 API 会产生费用（约 ¥0.1~0.3/张），需控制调用频次。
- 调用豆包 LLM 费用极低（约 ¥0.003/千 tokens），可忽略。
- 需可访问 `visual.volcengineapi.com` 和 `ark.cn-beijing.volces.com`（国内直连可用）。
- Python 3.11+，Node.js 18+。

### 8.2 假设
- MVP 阶段单用户使用，不做鉴权。
- 知识库内容手动维护，不做后台编辑。
- 不做 API Key 管理界面，密钥通过环境变量配置。
- 默认不启用 provider mock 降级：豆包 ARK 或即梦 API 连接失败时，任务直接标记 `failed` 并返回可读错误；仅开发调试时可显式开启 `MOCK_ON_LLM_FAILURE=true` 或 `MOCK_ON_API_FAILURE=true`。
- 不做多用户协作，任务归属固定 `default`。

### 8.3 不做的事（Out of Scope）
- 不做用户注册登录系统。
- 不做支付、订阅。
- 不做模型训练 / 微调。
- 不做移动端原生 App。
- 不做即梦 workflow 可视化编辑器（仅用预设的 3 个 workflow）。

## 10. 风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 即梦 API 鉴权 / 配额问题 | 阻塞第二阶段 | 提前开通服务并测试鉴权，准备好备用 Access Key |
